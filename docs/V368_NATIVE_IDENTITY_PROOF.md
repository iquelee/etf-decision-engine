## 固定验证顺序

1. 新函数/集合代码配置独立下载复核后，prepare一次创建新scope的schedule/control；所有固定主键必须不存在，不自动重置。
2. 通过SDK伪造完整Timer事件一次，要求原生来源拒绝发生在数据库访问之前。
3. 新单次Timer触发后，在本函数进程内走现有local root、签名worker和真实事务；只写一个合成业务标记。只有业务返回已确认且attempt已持久化SUCCESS，才主动抛一次固定错误以触发平台原生重试。
4. 原生重试Time必须仍匹配预先准备的发生时刻、逻辑ID一致，永久回执拒绝第二次业务，独立核验日志和七个最终文档。原生requestId可变化，不用它作业务身份。
5. 重试后再SDK伪造Timer一次，要求来源拒绝且落在至少一个原生attempt的同一温热实例。只命中冷实例不算通过，不为追求命中而加调用。来源若粘滞成timer，即使永久去重挡住业务，仍是来源资格失败。
6. audit一次只核验固定数据；它明确不自称完成温热SDK来源证明，后者必须由外部日志/调用收据独立比对。
7. 前述通过后才创建新HTTP路径，浏览器从固定127.0.0.1来源发一次无凭据POST，自动preflight，携带固定合成UUID的X-Writer-Operation-Id。必须真实浏览器跨源成功并由新函数回显确认。之后停用新路径一次，独立核验旧路由完全不变。

名义SDK调用4次、原生Timer2次、浏览器POST1次、OPTIONS可能0或1次函数执行，共7..8次；平台资源重试和公开路径在启用窗口内的外部命中不受该名义数硬限制。业务最多1次、固定最终文档最多7条。异常即停止后续步骤，按已封存应急动作关闭新入口并观察队列，不补造证据。
